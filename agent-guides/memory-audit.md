# Memory-safety audit checklist

## Recurring Memory-Safety Bug Classes (audit checklist)

Repeated audits of the driver keep surfacing the **same handful of defect shapes**, almost always at the boundary where C++ handles mudlib-, database-, or network-supplied data. When writing or reviewing any efun / package / VM code that touches memory, check for each of these:

1. **Unbounded copy of variable-length data into a fixed buffer.** LPC strings/arrays/buffers are arbitrary length -- use `SVALUE_STRLEN(sv)`, `arr->size`, `buf->size` (a `buffer_t`'s payload is `buf->item`, length `buf->size`). Never `strcpy`/`strcat`/`sprintf`/`memcpy` a mudlib/DB/network string into a `char buf[N]` without a bound; use `snprintf` or a length-checked `memcpy` + explicit NUL. Don't size a **stack VLA** from a config value (`char buf[CONFIG_INT(...)]`). (Codacy also flags `strncpy` as CWE-120; prefer `memcpy` with an explicit terminator.)
2. **Integer overflow / truncation before an allocation, `memcpy`, or index.** LPC ints are 64-bit (`LPC_INT`); an efun argument stashed in an `int` offset/length truncates or, if negative, becomes a huge `size_t`. Range-check offsets/lengths in the **non-truncating** type, and clamp `len * count` against the limit **before** multiplying (post-multiply the product has already wrapped).
   * **`-fwrapv` (`src/CMakeLists.txt`) makes plain `+`/`-`/`*`/unary-negate overflow on signed ints DEFINED** (silent two's-complement wraparound, not UB) -- LPC scripts can and do rely on this for `+ - * += -= *=`. This is consistent everywhere it's implemented: the runtime opcodes in `interpret.cc` and the `#if` evaluator in `lexer_rules_pp.cc` both do plain wraparound arithmetic for these three operators; the compile-time constant folder in `trees.cc` doesn't fold `+`/`-`/`*` at all (only `| ^ & << >> %`), so those always defer to the runtime path and there's no folded-vs-runtime discrepancy to check.
   * **"Defined" does not mean "safe" for a size, offset, or count.** A value that's allowed to wrap is still a memory-safety bug the instant it feeds a `DMALLOC`/`memcpy`/array index -- a wrapped-negative length becomes a huge `size_t`. Don't lean on wraparound to make a size computation safe; bound-check it explicitly *before* it can wrap (see `f_uncompress()`'s per-iteration `len` cap: checked every loop iteration, long before `len` could ever approach the type's range, not "after, and hope").
3. **`INT_MIN / -1` / `INT_MIN % -1`, and an out-of-range shift count** (negative, or `>=` the operand's bit width) **are undefined behaviour that `-fwrapv` does NOT cover** (it only defines overflow of `+`/`-`/`*`/unary-negate) -- both trip UBSan, and since the build sets `-fno-sanitize-recover=all` that's a hard process abort, not a warning. Guard every signed divide/modulo of LPC ints explicitly (the `-1` divisor/dividend cases), erroring cleanly. For shift, don't error at all: **mask the count to the low 6 bits (`& 63`) before shifting**, matching Java's `long` shift semantics (JLS 15.19) -- every LPC int becomes a legal shift count with a well-defined, deterministic result, instead of rejecting otherwise-ordinary scripts that happen to shift by a large or negative amount. Remember there are usually **three** parallel sites per operator that all need the identical treatment: the interpreter opcode / efun (`F_DIVIDE`/`F_MOD`, `f_div_eq`/`f_mod_eq`, `f_lsh`/`f_rsh`/`f_lsh_eq`/`f_rsh_eq`), the compile-time constant folder (`trees.cc`'s `binary_int_op()`), and the `#if` preprocessor evaluator (`lexer_rules_pp.cc`'s `ifexpr_binop()`) -- a folded and unfolded shift by the same count must agree.
4. **Recursion with no depth cap on attacker-nested data.** Deeply nested `({ ([ (:` in `restore_object` data, parser input, or compiled source overflows the C stack. Cap it -- the save AND restore paths share `MAX_SAVE_SVALUE_DEPTH`; other callers of nested-array-walking helpers (e.g. the parser's `environment` argument) need their own explicit depth parameter if they don't already have one.
   * **Every sibling walker over the same recursive structure needs its OWN cap.** When a parse tree / save-svalue / whatever gets a depth cap on one recursive walker, the *other* walkers over the identical shape are still uncapped and still crash. The compiler tree has THREE: `optimize()` (generate.cc), `i_generate_node()` (icode.cc), and `ast_json()`/`dump_tree()` (generate.cc, the `lpcc --ast` renderer) -- the first two were capped (117cbc1) and the third was missed, so `lpcc --ast` on a deeply-nested expression still segfaulted before codegen's cap could reject it. Grep for every function that recurses on the same node/element type and confirm each has the guard. **The PREPROCESSOR's former recursion siblings were ELIMINATED, not capped** (the better fix when feasible): the whole macro/lexing layer is now iterative -- the rescan expansion continues in the SAME `yylex()` frame (`LPC_TOKEN_RESCAN` fall-through, one Flex buffer per level), `lpc_lex_expand_string()` (function-like-macro **argument pre-expansion** and unquoted `#include` filenames -- a chain of DISTINCT macros `A->B->C->...` that the self-reference guard does NOT bound) is an explicit work-stack machine, the `#if`/`#elif` evaluator (`ifexpr_eval` in `lexer_rules_pp.cc`, depth = paren/unary/ternary nesting) is an explicit-stack machine, and the lexer's no-token retries (heredoc recovery, over-long `$N`, template `}`) fall through instead of recursing into `yylex()`. Both expansion engines share ONE generous runaway bound, `kLpcMaxExpansionNesting` (65535, counted in LIVE frames) -- a memory bound, not a stack-safety bound. Pinned by `compiler/deep_macro_nesting.lpc`, `compiler/lexer_retry_chains.lpc`, `compiler/deep_nesting_caps.lpc`.
   * **Size any remaining cap against the SANITIZER build's stack, not a "plausible" number -- or better, remove the recursion.** ASan/UBSan redzones inflate every C frame, so a cap that's safe on a release build can still overflow the C stack on the Debug+sanitizer build that CI runs. `kMaxOptimizeDepth`/`kMaxGenerateNodeDepth` are deliberately 500 (not thousands) for this reason; the preprocessor's old recursive design had exactly this failure (its 128 cap sat above the sanitizer build's ~70-80-frame crash boundary, so the cap never fired) and was briefly lowered to 32 before the recursion itself was eliminated -- a cap that must sit under the *sanitizer* stack budget is usually small enough to reject legitimate programs, which is the signal to convert the walker to an explicit heap stack instead (a 60000-deep chain now compiles under ASan). When a cap must stay (the parse-tree walkers), bisect the real crash boundary on the sanitizer build and set it comfortably under.
5. **Missing type / bounds checks on stack arguments.** Spec-declared types cover only the first few fixed args; `varargs`, index, and count args still need explicit validation (an array indexed by an LPC int; a matrix that must have 16 elements; a port index bounded by **element count**, not `sizeof(array)` which is the size in *bytes*). Note this is about **element-level or varargs-position** checks specifically -- see packages.md "Generic Argument Type-Checking" for what the dispatcher already covers for free at the top level, so you don't file (or re-fix) a false positive.
6. **Tainted format strings.** `error()`, `debug_message()`, `debug()`, `yyerror`/`yywarn`/`lexerror`, and `telnet_printf` are printf-style. Any source-, mudlib-, DB-, or network-derived text (filenames, object paths, verbs, identifiers, `#error` payloads, DB error strings) must be a **`%s` argument**, never the format string -- a stray `%` is a crash / CodeQL `cpp/tainted-format-string`. Distinct but adjacent bug: a format specifier that doesn't match its argument's actual C++ type (e.g. `"%d"` for an `LPC_FLOAT`/`double` vararg) is also UB and prints garbage -- `error()` has no `format(printf, ...)` attribute, so the compiler won't catch this for you; make sure the value you pass is actually the type the specifier expects.
7. **Leaks & dirty state on `error()` paths** -- see memory.md (refs, half-filled VM stack slots, module-global scratch state, and the "deep C-style call chain" case where you must abort via plain `return`s instead of `error()`).
8. **Off-graph & cross-thread references invisible to the debug ref-count checker** -- see memory.md (add a `*_mark` function; mark transitively; lock-guard and cover every concurrent worker).
9. **Per-instance state parked in a shared global.** Index lvalues used to live in `global_lvalue_byte` / `global_lvalue_codepoint` / `global_lvalue_range` (issue #1358); they are now stack-resident. Anything that can be active twice concurrently still must keep instance state on the VM stack (or in the owning `ref_t`), not in a file-scope singleton. Nested string `foreach` segfaulted when the inner loop reset a shared EGC iterator. Also: any operator handling `T_LVALUE_BYTE` must handle `T_LVALUE_CODEPOINT` too (see lpc-runtime.md "String-Char Lvalues").
   * **The compiler has the same shape, and Bison's reduction order hides it.** `current_type` is a file-scope global holding the type of the declaration being parsed, and a declarator's rule reads it in the action that runs AFTER its initializer has been parsed. Any construct that can contain a declaration inside an initializer therefore has to save and restore it: `mixed e = catch { float f = 1.0; };` left `current_type` at `float`, so `e` was declared float and a later `e = 5;` silently stored `5.000000` (or, when the stolen type was not coercible, produced a type error on a line unrelated to the cause). The block-expression constructs (`catch {}`, `time_expression {}`) already saved the `context` flags this way, on Bison's own value stack via their `*_context_start` mid-rule action -- which is the right vehicle, because a value on the parser stack is discarded with it and a parse error cannot desync it the way a side stack would (cf. item 13). Anonymous functions were the one construct that got this right. When adding a construct that can hold a block in expression position, save everything the block can clobber, not just the flags you were thinking about.
10. **Signaling failure via an out-of-band sentinel value instead of a real out-parameter.** Returning a special "impossible" value (e.g. `-INT_MAX+1`) from a helper to mean "this failed," with the caller comparing the *actual* result against that sentinel, is unsound the moment the return type can legitimately produce that exact value -- a large-magnitude but perfectly correct `LPC_FLOAT` result silently collided with the sentinel and got misreported as an error. Use an explicit status out-parameter (`bool*`, or a small `int` status/error code) so success can never be confused with a real computed value. (Seen: `math.cc`'s `norm()`/`vector_op()`/`dotprod()`/`distance()`/`angle()`.)
11. **A per-instance operation that mutates a shared/copied lvalue must update ALL of that value's state, not just the numeric payload.** `svalue_t` carries side-channel state (`subtype`, e.g. `T_UNDEFINED`) alongside `u.number`/`u.real`; a compound assign that does `argp->u.number OP= rhs` but leaves `argp->subtype` untouched leaves stale side-channel state on an otherwise-correctly-computed value (here: a variable that started "undefined" kept reporting `undefinedp() == 1` after a real arithmetic result was computed into it). When you touch an lvalue's payload, check whether its type also carries subtype/flag bits that need resetting to match the new, real value.
12. **A driver-internal backtracking/recursive search with no step budget is invisible to the LPC eval-cost limiter.** `max_eval_cost` only meters LPC bytecode; a C++ search that tries every split/position combination for a crafted-but-legal input (e.g. a parser rule with several unbounded-span tokens against a long sentence) can run for a very long time before concluding "no match," completely ungoverned by the normal timeout. Add an explicit step counter with a generous-but-finite cap; see memory.md's "deep C-style call chain" entry for how to abort it without leaking.
13. **A depth-capped push/pop pair whose over-cap push is a SOFT (non-throwing) no-op desyncs the paired stack.** When a fixed-size context stack (`function_context_stack[MAX_FUNCTION_DEPTH]`, an include stack, etc.) reports "too deep" via `lexerror()`/`yywarn()` -- a *soft* diagnostic that records the error and returns normally rather than throwing -- and then silently skips the push, the caller (usually the grammar) still emits exactly one matching pop later. Those extra pops walk the shared "current" pointer past its real root into `nullptr` and the next dereference segfaults. Either mirror the skip on BOTH sides (a saturating counter: increment on a skipped push, and have pop consume that budget before touching the real stack -- what `failed_function_context_pushes` in `lexer_utils.cc` now does for nested `(: :)` past `MAX_FUNCTION_DEPTH`), or push a sentinel context so every pop still has something valid to walk. This is the compiler-front-end sibling of the interpret.cc "one arm forgot what its sibling arm does" stack-imbalance class.
14. **A cached raw handle can outlive the resource it was derived from, and a C callback can free the resource it is running inside.** Two shapes seen in `package/ffi`: (a) `FfiFunc` cached a raw `dlsym()` address with no back-reference to the `dlopen()` handle it came from, so `ffi_unload()`'s `dlclose()` left every prepared function's `->addr` pointing into unmapped memory -- a later call jumped into it. Give the derived handle a link back to its owner and invalidate (or refuse to free while outstanding) rather than leaving it dangling. (b) A libffi closure (`closure_dispatch()`) runs arbitrary LPC, which can call `ffi_callback_free()` on the *very callback currently dispatching* -- freeing both the `FfiCallback` it's about to read from AND the trampoline still on the C stack. Copy every field you still need into a local before calling into LPC, and refuse to free a callback while its `dispatching` flag is set. General rule: any C structure that survives across a call into arbitrary LPC (an apply, a callback, `__INIT`) can be freed or destructed by that LPC -- re-validate or pre-copy, exactly as memory.md's `destruct_object()` stack-sweep note requires for object arguments.
15. **A serializing/ownership primitive that only SOME of the sibling paths take.** Two shapes of the same "one path forgot what its siblings do" mistake: (a) **a flag the teardown path keys on.** `destruct_object()` only force-closes an object's efun sockets when `O_EFUN_SOCKET` is set. `socket_create()`/`socket_accept()`/`socket_connect()` all set it alongside `owner_ob = current_object`; `socket_acquire()` set the owner but NOT the flag, so destructing an object that acquired (rather than created) a socket skipped `close_referencing_sockets()` and left `owner_ob` dangling. (b) **a lock the concurrent worker takes.** `package/async` runs `db_exec` queries on a detached worker thread that locks `db_mut` around its `find_db_conn()`+`execute()` on the shared `db_conn_list`/`dbconn_t`; only the sync `f_db_exec()` took that same lock, while `f_db_close()`/`f_db_fetch()`/`f_db_commit()`/`f_db_rollback()`/`f_db_status()` touched a live connection with no lock -- a concurrent `async_db_exec()` + main-thread `db_close()` on the same handle is a use-after-free (close frees the `dbconn_t` the worker is mid-execute on). When several code paths establish the same ownership relationship OR touch the same shared resource, every one of them must set the same flag / take the same lock -- grep for the sibling paths and diff what each does. (This DB race, like the socket flag, has no single-file `-ftest:` regression route -- it needs a real worker thread racing the main thread -- so it's fixed on code-symmetry per the note below.)

16. **`st_num_arg` is a bare global clobbered by ANY nested LPC -- latch it before calling anything that can apply.** Every efun dispatch (and `call_function_pointer`) overwrites `st_num_arg`; it is never saved/restored across a master apply. An efun that calls `check_valid_path()` (= `valid_read`/`valid_write` master apply) or any other apply, and THEN reads `st_num_arg` (to detect an optional trailing argument, or inside `process_efun_callback()`), reads the arity of whatever efun the mudlib's apply called last -- mispopping the VM stack (Debug: `fatal("Bad sp")`; release: stack desync / wrong-slot funptr ref++). Latch `int const num_arg = st_num_arg;` FIRST, and restore `st_num_arg = num_arg;` after the applying call if anything downstream (e.g. `process_efun_callback`) reads the global. `f_async_db_exec`'s ordering comment documents the original crash; the async_read/write/getdir promise forms re-introduced it by hoisting `check_valid_path()` above the branch. The testsuite master's `valid_read`/`valid_write` now deliberately call efuns of differing arities so this class fails the suite instead of hiding behind a master that "conveniently" calls nothing. **Those live in `testsuite/inherit/master/valid.lpc`, which `/single/master` INHERITS -- so defining any `valid_*` directly in `single/master.lpc` shadows the canary and silently switches it off.** It also switches off the run's `inherit_called` counter, whose only symptom is the misleading `MASTER valid inherit functions are not being called!` at the end of a single-file run. If a test needs special-case behaviour from one of those applies, special-case the one path and `return ::valid_read(...)` for everything else.
17. **Bytecode is unsigned; `char*` is signed.** Any consumer that fetches an opcode or a byte operand via plain `*pc++` sign-extends values >= 128 -- every `case F_FOO:` for a high opcode is silently dead and the decode desyncs on its operand bytes. The interpreter uses `EXTRACT_UCHAR`; secondary consumers (the disassembler was one) must too. When ops.spec growth first crosses an opcode past 127, grep every `= *pc` in non-interpreter decoders. **Note also that APPENDING to `ops.spec` is not opcode-stable the way it sounds**: the operators there are numbered before the efuns, so three new operators shift every efun opcode up by three. Nothing persists bytecode today (programs are compiled from source at load and never serialised; `backend.cc`'s "swapping" is reset/clean_up only), so this is currently harmless -- but it is what pushes opcodes past 127 in the first place.
18. **A one-flag "scheduled" latch cannot express "reschedule LATER than the pending event."** `schedule_drain()`-style guards (`if (!scheduled) { scheduled = true; add_event(delay); }`) look correct until one caller needs a DIFFERENT delay: the promise drain's budget-exhaustion path wanted next-tick, but a mid-drain settle had already armed a same-tick event and set the flag, making the deferral a silent no-op -- and `call_tick_events()` services same-tick insertions in the same invocation, so the "deferral" re-entered immediately with a fresh budget (a wedge). Keep the `TickEvent*` returned by `add_gametick_event()` and invalidate (`event->valid = false`) the pending event before re-arming with the new delay. Empirically verify deferral fixes by actually driving the loop past the budget: the no-op version passes every ordinary test.

19. **`current_prog` is the DEFINING program, not the object's.** `setup_new_frame()` retargets `current_prog` to `prog->inherit[n].prog` for an inherited function, so anything that snapshots `current_prog` and later compares it against `ob->prog` is wrong for every inherited function -- and *right-looking* for every locally defined one, so a test that only exercises a local function passes. (Seen twice in one feature: a parked coroutine's staleness guard rejected every inherited `await`, and the same confusion hid the real `replace_program()` hazard, since replace makes `ob->prog` EQUAL the defining program.) Snapshot `current_object->prog` separately when you mean "the object's program", and note that offsets like `variable_index_offset`/`pc_offset` are relative to the DEFINING program, so both are needed.
20. **A parallel table indexed by an enum must grow with the enum -- and the compiler will not tell you.** `lpc_tree_name[]` (node kinds) and `checkmemory.cc`'s `sources[]` (DMALLOC tags) are `const char*[]` initializer lists indexed by a value whose range is defined elsewhere; adding `NODE_ACATCH` / a new `TAG_*` silently produced an out-of-bounds read (segfault). Prefer an accessor that bounds-checks and returns a placeholder (`source_name()`) over trusting the tables to stay in step; when adding an enum member, grep for tables indexed by that enum.
21. **A "type name" printer that walks a contiguous bit window silently omits any tag outside it.** `type_names[]` + the `TYPE_CODES_START..TYPE_CODES_END` walk in `bad_argument()`/`bad_argument_multiple_types()`/`add_svalue_type_name()` covers only the low `T_*` bits; `T_PROMISE` (0x10000) rendered as nothing at all, so every promise-typed efun's error read `Expected:  Got: 1.` Teaching `type_name()` alone is not enough -- there are four renderers, three of them bit-walkers.
22. **Widening the meaning of a compiler `context` bit changes what `break`/`continue` accept.** Making `await` illegal inside a loop nested in `catch {}` by carrying `SPECIAL_CONTEXT` through loop/switch entry also made `for (...) { break; }` *inside* a catch block a compile error -- long-standing, perfectly legal mudlib code, and no test covered it. Keep "a jump here would cross the boundary" (cleared by a loop, since the loop is the jump target) separate from "no suspension anywhere below here" (carried through): that is why `NO_SUSPEND_CONTEXT` exists alongside `SPECIAL_CONTEXT`. When touching `context` flags, compile a matrix of break/continue/switch inside catch/time_expression/acatch, nested both ways.
23. **A scheduler that meters units of work must bound the BATCH without truncating a unit.** The promise microtask drain hands out deliveries (resumed `await` frames, `.then` handlers); each is a scheduled unit like a `call_out` callback and gets a whole `maximum evaluation cost` of its own, so it always runs to its natural end. The turn budget (`async drain eval budget`) governs how many a turn STARTS, never interrupts one in flight. Sharing ONE budget across the turn was tried and is wrong: it kills an innocent handler with "Too long evaluation" for time the handlers ahead of it spent. But a pure *count* per turn is wrong too -- N deliveries at a full budget each is an N-times-the-limit freeze (measured at 17-21 seconds with a count of 512). The bound has to be accumulated elapsed time, and the worst case is then `turn budget + one delivery`.
    * **Prefer the flag over any clock where the flag can answer.** `outoftime` is a `volatile int` the SIGVTALRM handler sets; `eval_instruction()` tests exactly that once per opcode, essentially free. It answers "did the thing I just ran burn its whole budget" exactly, and the drain uses it as a second, free turn-ender. What it cannot answer is "how much has this batch accumulated across many cheap units", because every unit re-arms it -- that one needs a real measurement, and `steady_clock::now()` (a ~20ns vDSO read of the same CLOCK_MONOTONIC the eval timer uses, so elapsed microseconds ARE eval cost) beats `get_eval()` (a `timer_gettime(2)` syscall). Two things to know when reading the flags outside the interpreter: interpret.cc RE-ARMS the timer and sets `max_eval_error = 1` *before* throwing "Too long evaluation" (so after an eval error the timer is not the signal -- the flags are), and `error_handler()` forces `outoftime` back on for an eval-cost error precisely so a `catch` cannot swallow it. `pop_control_stack()` saves and restores it around `defer()` handlers, so it survives teardown. Whatever reads the flags this way must clear both on the way out, or an exhausted budget leaks into whatever the backend runs next.

24. **A function the DRIVER calls cannot return a value the driver does not understand.** An apply's return value is read the instant it returns, by C++ that switches on a small set of `T_*` tags -- and the "unknown tag" arm is usually the PERMISSIVE one. `check_valid_path()` denies only on `T_NUMBER && == 0` and treats anything else as allow, so an `async int valid_read()` (which returns a `T_PROMISE` the moment its body parks) granted access unconditionally, whatever the body decided. Before letting a new value type reach an apply's return, grep the consumers for what they do with a tag they do not expect; where the answer is "fall through", the new type is a silent security bypass, not a type error. `define_new_function()` refuses `async` on the generated `object_applies_table[]` (warns on the master-only rest of `all_applies_table[]`) for exactly this reason -- and both tables are GENERATED from `vm/internal/applies` rather than hand-copied, because a hand-maintained second list of applies is the memory-audit.md item 20 parallel-table trap waiting to happen. **But a name-based compile check is a LINT, never the boundary**: it keys on the declaration, so it cannot see an ordinary apply that RETURNS the result of an async call (`mixed id(string s) { return slow(); }` -- verified to make `present()` match any name), and it cannot cover `add_action()` verb functions, whose names are arbitrary mudlib strings. Fix the CONSUMER, and treat the compile check as a courtesy. The full sweep turned up two more shared expressions with the same shape, each behind many gates: **`MASTER_APPROVED()`** (`vm/internal/master.h`) approved on `type != T_NUMBER`, i.e. on a promise, across `valid_seteuid`, `valid_bind`, `valid_shadow`, `valid_socket`, `valid_object`, `valid_link`, `valid_hide` and `valid_override` -- it is now `master_approved(v, apply_name)`, which denies a `T_PROMISE` and names the gate in the log; and **`IS_ZERO()`** used as "did the object say yes", which made `present()` match an object whose `id()` returned a promise and made the parser set `is_living`/`inventory_accessible`/`inventory_visible`/`livings_are_remote` from one -- those seven sites now use `APPLY_SAYS_YES()`. `user_parser()` likewise treats a verb function that returns one as having DECLINED the command (its "handled" test was `non-zero and not the number 0`, so a parked verb silently consumed the command, skipped the remaining sentences on that verb and suppressed `notify_no_command()`). **Do NOT change `IS_ZERO` itself**: its other uses are ordinary LPC callbacks (`filter`, `map`, `sort_array`, ...) where a promise is true exactly as it is to the equivalent hand-written `if (cb(x))` -- a language decision, not a bug. The distinction to hold onto is *the driver asking a question* versus *LPC using a value as a truth value*. Two further traps found the same way: the driver also dispatches applies that are NOT in `vm/internal/applies` at all (`heart_beat` goes through a cached `prog->heart_beat` index; `is_living`, `query_light`, `the_short` and the rest of the parser/dwlib applies are applied by their packages), so "the table" is not the whole set of names the driver calls.

25. **Handing LPC a first-class handle to a channel the DRIVER will complete makes the mudlib a competing writer -- and "first write wins" loses the driver's answer silently.** `promise_settle()` is first-settle-wins and returns 0 on the loser with no diagnostic, which is correct for a race between two *equal* claimants. It is not correct when one of the two claimants is the driver delivering a computed result: `promise_reject(p)` on the promise of a still-parked `async` function was accepted, the body then resumed, ran to completion and had its `return` value dropped -- no error at the reject, none at the return, and nothing to observe the loss from. It also was not the cancellation it resembled (the body kept running, kept its object alive and kept its `max suspended async functions` slot); it only discarded the caller's view. So decide, **per handle source**, who owns the completion, and refuse the other side explicitly (`promise_t::body_owned`, checked in `f_promise_resolve`/`f_promise_reject` *after* the already-settled guard, so a finished body still reports the more specific "already settled"). **Then audit the sibling sources rather than assuming the rule generalizes**: `call_out(delay)`, `async_read`/`async_write`/`async_getdir`, `promise_then()`'s chained promise and `async_yield()` all hand out driver-settled promises too. Mudlib settling of those is *deliberately* still allowed, but be honest about why, because it is NOT that they are harmless. They are memory-SAFE (every driver-side settle guards on `state == PROMISE_PENDING`, or on `resolving` for `async_yield`), and for `call_out(delay)`/`async_yield()` the discarded value really is informationless (a timer tick, `0`). For the other two it is not: a pre-settled `async_read` promise silently drops the file contents, and pre-RESOLVING one turns an I/O failure into an apparent success; `promise_then()`'s chained promise is the handler's result channel and drops the handler's return value exactly as the async body did. Those stay settleable because a consumer-side timeout (`call_out((: promise_reject(p, "timeout") :), 10)`) is the only way to bound a wait until real combinators exist -- a deliberate trade, not an absence of harm. The async body was fixed first because it is the one a user was actually bitten by, and because an LPC caller can never otherwise make `f()`'s call site observe a value `f` did not return. When you add a new promise source, decide which side of that trade it is on and say so. Reported from real mudlib use, not by any audit -- the shape is invisible to the ref-count checker and the sanitizers because nothing is corrupted, only forgotten.

**Validate a fix** on **Debug + ASan/UBSan AND RelWithDebInfo** (some bugs are release-only, some only trip the sanitizers), run the LPC suite 2–3× (randomized order), and add a regression under `testsuite/single/tests/` that demonstrably fails on the unfixed binary (see testsuite.md). **Some crash paths have no driver-LPC regression route** -- a bug reachable only from the offline `lpcc` tool (e.g. `ast_json()`/`dump_tree()`, which no efun invokes) or one that needs real async socket/event-loop timing a single-file `-ftest:` run can't service (e.g. the `socket_acquire()` dangling-owner UAF, since call_outs and network events don't fire in single-file runs -- see testsuite.md). For those, drive the closest observable behaviour you can, lean on `src/tests/` GTest unit tests, and rely on the code-symmetry argument (the fix matching its siblings) rather than forcing a flaky end-to-end test.

**Three cheap ways to find orderings nobody wrote a test for** -- each has paid for itself:

* **A ThreadSanitizer build.** `ENABLE_SANITIZER` is ASan+UBSan only, and TSan needs its own build directory (it is incompatible with ASan). It also needs **`-DUSE_JEMALLOC:BOOL=OFF`**: `src/CMakeLists.txt` force-disables jemalloc for Debug and for ASan but NOT for TSan, and a jemalloc'd TSan binary segfaults during interceptor init (`dlsym` -> `malloc` -> jemalloc's `malloc_init_hard` -> a TSan `pthread_mutex_trylock` interceptor whose real function is not resolved yet) with **no output at all**, which reads like a driver crash and is not one. Working recipe: `-DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ -DUSE_JEMALLOC:BOOL=OFF -DPACKAGE_DB:BOOL=OFF -DMARCH_NATIVE=OFF -DCMAKE_{C,CXX}_FLAGS="-fsanitize=thread -g" -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread`. Known benign report to suppress: libevent writes its global `event_debug_mode_too_late = 1` outside `event_debug_map_lock_` (`event_debug_note_setup_`/`_teardown_`); every writer stores the same constant, and `evthread_use_pthreads()` IS called, so libevent's real state is locked.
* **A hostile-config matrix.** Re-run the suite with each tuning knob at its pathological end (`async drain eval budget : 1`, `max suspended async functions : 4`, `gametick msec : 1` and `: 5000`, `call_out(0) nest level : 1`). Most resulting failures are the config doing what it says, and triaging them is the point: it separates "the driver is wrong" from "this test encodes a default-config timing assumption". Two things to know before reading the results -- a **5000ms gametick collapses `call_out(...,1)` and `call_out(...,3)` into the same tick**, so any test that sequences phases with second-scale call_outs fails there for free; and a **test that checks a promise delivery after a fixed delay is measuring throughput**, since `async drain eval budget : 1` (one microsecond, i.e. one delivery per loop turn) caps throughput hard. Drive such a check FROM the delivery (a handler that releases its exit latch), never from a deadline.
* **A seeded LPC lifecycle fuzzer.** `testsuite/single/tests/efuns/async_lifecycle_fuzz.lpc` is the worked example: a fixed-seed LCG picks from a set of destructive operations (park in several shapes, settle, reject, drop the last reference, destruct, recompile) against a pool of clones, re-checks the subsystem's own invariants after EVERY step, and additionally performs destructive operations from INSIDE a reaction handler so they land between two deliveries of one drain batch rather than only between gameticks. Fix the seed (a fuzzer in CI has to fail the same way twice) and assert coverage at the end (`the chaos path never executed`), or a refactor can silently disconnect the interesting paths and the run still looks clean. It found a real accounting defect on its first run.

The 2026-07-20 stability-audit fixes for this whole checklist live as regression tests under `testsuite/single/tests/` (`crasher/disassemble_wide_push.lpc`, `compiler/deep_nesting_caps.lpc`, `compiler/default_args_error_unwind.lpc`, `efuns/restore_variable_class.lpc`, `efuns/ffi_lifecycle_safety.lpc`, `efuns/error_handler_mapping_size.lpc`) -- each drives a fixed path and asserts a clean error / no crash / (on Debug) no `check_memory()` ref-count report.
